# 29. 可视化审批流程设计（方案稿 v2）

> 适用版本：CRM 2.12 · 状态：**已落地（本地，未上传实例）** · 功能落点：系统设置 → 审批流程设计器

## 1. 一句话结论

**新安装默认启用「官方预设」审批流程**，它与当前系统内置的两条审批链完全等价；超级管理员（角色 `admin`）可以在系统设置里用**可视化画布**调整条件、节点和审批人，发布后新单据按新流程走，进行中的单据不受影响。老实例升级不自动切换，保持原行为。

设计上只替换「这条单据该走哪些节点」的生成环节；审批决策、管理员代审 / 一键通过、报价与合同业务联动全部保持原样。

---

## 2. 现状盘点

| 环节 | 现在的实现 | 位置 |
|---|---|---|
| 报价折扣链 | `chainForDiscount(rate, orgId)`：按折扣率与经理/总监阈值追加 `manager → director → gm`；个人 `discount_limit` 可覆盖角色阈值 | `src/approval.js:30` |
| 合同审批链 | `chainForContract({amount, paymentTerms, nonStandard})`：`manager → director? → finance → legal?` | `src/approval.js:52` |
| 阈值配置 | 7 个 `approve.*` 设置项，只能填数字，不能改节点顺序、不能加节点 | `src/settings.js:7-21` |
| 审批人解析 | `approverCandidates()` 沿 `org_units.path` 由近及远找在职角色，职能角色全局兜底 | `src/approval.js:91` |
| 节点落库 | 提交时 `resolveChain()` 把「角色」解析成「具体人」，写进 `approval_steps` 快照 | `src/approval.js:131,186` |
| 审批决策 | 逐级流转；管理员可审任意节点、可一键通过剩余全部，代审留痕 | `src/approval.js:236` |
| 业务联动 | 审批结束后 `applyBusiness()` 改报价/合同状态、生成回款计划、回写商机 | `src/approval.js:306` |
| 设置页 | 全员可见只读、管理员可改；schema 驱动的简单表单 | `public/js/views/settings.js`、`src/routes/admin.js:367` |

**结论**：问题不在审批引擎，而在「链怎么定」不可配。改造面收敛在链生成、配置存储与可视化编辑，不动决策与业务联动。

## 3. 范围边界

### 3.1 首期做

1. 新安装默认写入**官方预设流程**并启用；老实例升级保持旧行为，不隐式切换。
2. 覆盖两类单据：`quote_discount`（报价折扣）、`contract`（合同审批）。
3. 超级管理员可在可视化画布上调整规则条件、节点顺序、审批人来源与节点选项。
4. 规则按优先级**首次命中**；支持「免审批」结束节点。
5. 审批人支持**按角色沿组织树解析**与**指定具体用户**两种来源。
6. 编辑先生成草稿，发布才生效；每次发布生成新版本，进行中的单据不受影响。
7. 提交前预览 / 试运行：显示命中规则、节点与具体审批人。
8. 全员可读、管理员可改；配置变更写审计日志。

### 3.2 首期不做

| 不做 | 原因 / 后续 |
|---|---|
| 会签、或签、并行节点 | 需要改造 `decide()` 状态机，风险高；列为 v2 |
| 超时自动通过、自动提醒 | 需要定时任务与通知通道，独立议题 |
| 条件嵌套（AND/OR 混排）、脚本条件 | 首期平铺 AND + 计算字段，已能表达官方预设 |
| 更多业务类型（开票、合同终止、回款） | 先把两类跑稳，再按同一模型扩展 |
| 修改已发起审批的流程实例 | 已发起单据保持快照；管理员可代审或驳回后重提 |
| 引入外部工作流引擎 | 与现有轻量架构不匹配 |

## 4. 默认官方预设

### 4.1 什么叫「按照官网的」

新装实例的审批链就是产品对外展示的标准流程，即当前 `chainForDiscount` / `chainForContract` 的行为。它不是一张空表，而是**预置好的、可查看可编辑的、带「官方预设」标记的流程版本**。

| 时机 | 行为 |
|---|---|
| 全新安装（管理员创建向导） | `src/routes/setup.js` 创建管理员时写入官方预设：`source='official'`、两类单据各一组规则，`state='active'`、`version=1`；同时把 `approval.custom.enabled` 写为 `'1'` |
| 老实例升级 | DDL 只建表补列，**不写入规则、不改开关**；`approval.custom.enabled` 读默认值 `'0'`，行为与现在完全一致 |
| 管理员改流程 | 点「可视化编辑」自动复制官方预设为草稿；官方预设本身只读保留 |
| 管理员想还原 | 点「恢复官方预设」，停用自定义草稿并重新激活官方版本，无需手写规则 |

`approval.custom.enabled` 在 `DEFAULTS` 中保持 `'0'`（保护升级实例），由安装向导显式写 `'1'`。原始阈值设置项继续保留，官方预设通过「计算字段」引用它们，所以改阈值时预设行为同步跟着变，不会出现两套数字打架。

### 4.2 官方预设规则

**报价折扣 `quote_discount`**

| 优先级 | 规则名 | 条件 | 节点 |
|---|---|---|---|
| 10 | 零折扣免审 | `discount_rate eq 0` | 免审批（`auto_approve=1`） |
| 20 | 经理审批 | `discount_rate gt 0` 且 `discount_rate lte manager_limit` | 部门经理 |
| 30 | 经理 + 总监 | `discount_rate gt manager_limit` 且 `discount_rate lte director_limit` | 部门经理 → 销售总监 |
| 40 | 大额让价 | `discount_rate gt director_limit` | 部门经理 → 销售总监 → 总经理 |
| 9999 | 兜底 | 无条件 | 部门经理 |

`manager_limit` / `director_limit` 是计算字段：先取该角色审批人的个人 `discount_limit`，没有则取 `approve.discount.manager` / `approve.discount.director`。这样个人限额覆盖角色的旧行为被完整保留。

**合同审批 `contract`**

| 优先级 | 规则名 | 条件 | 节点 |
|---|---|---|---|
| 10 | 法务 + 总监 | `trigger_legal eq 1` 且 `trigger_director eq 1` | 部门经理 → 销售总监 → 财务审核 → 法务审核 |
| 11 | 法务介入 | `trigger_legal eq 1` 且 `trigger_director eq 0` | 部门经理 → 财务审核 → 法务审核 |
| 20 | 总监审批 | `trigger_director eq 1` 且 `trigger_legal eq 0` | 部门经理 → 销售总监 → 财务审核 |
| 30 | 标准合同 | `trigger_director eq 0` 且 `trigger_legal eq 0` | 部门经理 → 财务审核 |
| 9999 | 兜底 | 无条件 | 部门经理 → 财务审核 |

`trigger_director = 金额 > amount_director 或 账期 > terms_director`；`trigger_legal = 金额 > amount_legal 或 账期 > terms_legal 或非标准条款`。两者由设置阈值实时计算，预设无需写死金额。

## 5. 配置模型

### 5.1 设置开关

`src/settings.js` 的 `DEFAULTS` 增加 `approval.custom.enabled='0'`；文案说明：关闭时走旧阈值链，开启时由审批流程设计器决定；新安装由向导自动开启。

### 5.2 新增表

放在 `src/db.js` 的 DDL 区，沿用 `SERIAL PRIMARY KEY` 双引擎写法（`ensureColumns` / PG 迁移同步补齐）。

**`approval_flows`（规则）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | SERIAL PK | 规则 id |
| `biz_type` | TEXT | `quote_discount` / `contract` |
| `name` | TEXT | 规则名 |
| `version` | INTEGER | 每次发布 +1 |
| `state` | TEXT | `draft` / `active` / `disabled` |
| `source` | TEXT | `official`（预设，只读） / `custom`（管理员编辑） |
| `priority` | INTEGER | 小号先匹配，同号按 id |
| `conditions_json` | TEXT | AND 条件数组，见 5.3 |
| `auto_approve` | INTEGER | 1 = 命中即免审批（steps 必须为 0） |
| `created_by` / `updated_by` | INTEGER | 操作人 id |
| `created_at` / `updated_at` / `published_at` | TEXT | 时间 |
| `fallback` | INTEGER | 1 = 兜底规则，不可删除，条件恒空 |

版本口径：**同一单据类型的一整套规则共享一个 version**，一个版本内有多条 `active` 规则（按 priority 排序）；切换版本时先把该类型所有 `active` 行改为 `disabled`，再把目标版本的草稿整批置为 `active`。每类单据恰好一条 `fallback=1`。

**`approval_flow_steps`（节点）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | SERIAL PK | 节点 id |
| `flow_id` | INTEGER FK | 所属规则 |
| `seq` | INTEGER | 从 1 开始 |
| `name` | TEXT | 显示名 |
| `approver_mode` | TEXT | `role`（沿组织树） / `user`（指定人） |
| `role` | TEXT | 角色键，来自 `ROLES` |
| `user_id` | INTEGER | `mode=user` 时用户 id |
| `allow_change` | INTEGER | 提交时是否允许在候选人中改选 |
| `on_missing` | TEXT | `block` / `admin` |
| `skip_duplicate` | INTEGER | 与上一节点同一人时跳过，默认 1 |
| `allow_self` | INTEGER | 允许申请人审批自己，默认 0 |
| `require_comment` | INTEGER | 该节点是否必须填意见 |
| `stage` | TEXT | `sales` / `finance` / `legal`，合同推导初始状态 |

### 5.3 条件语法与计算字段

`conditions_json` 是平铺 AND 数组：

```json
[
  { "field": "discount_rate", "op": "gt",  "value": 10 },
  { "field": "amount",        "op": "gte", "value": 500000 }
]
```

- 运算符：`gt / gte / lt / lte / eq / ne / in`（`in` 的 value 为数组）。
- 报价原始字段：`discount_rate`、`amount`、`has_custom`、`org_id`、`applicant_role`。
- 报价计算字段：`manager_limit`、`director_limit`（见 4.2）。
- 合同原始字段：`amount`、`payment_terms`、`non_standard`、`has_quotation`、`org_id`、`applicant_role`。
- 合同计算字段：`trigger_director`、`trigger_legal`（见 4.2）。
- 发布时校验字段名与类型；运行期未知字段按「不匹配」处理并写审计，不静默放行。

### 5.4 现有表只补追溯列

- `approvals`：`flow_id`、`flow_version`、`rule_id`、`flow_source`。
- `approval_steps`：`approver_mode`、`flow_step_id`。
- 历史数据为 NULL，一律按旧逻辑解释；`approver_id` 的快照语义不变。

## 6. 规则求值链

```
提交报价 / 提交合同
   │
   ├─ 构造上下文 buildApprovalContext(bizType, record)
   │     原始字段 + 计算字段（阈值来自当前 settings）
   │
   ├─ approval.custom.enabled = 0 ?
   │     └─ 是 → chainForDiscount / chainForContract（完全保持现状）
   │
   └─ 否 → 读该 biz_type 的 active 流程版本
         ├─ 按 priority 顺序逐条匹配，首个命中即停
         ├─ 命中 auto_approve → 空链，走「免审批」分支
         ├─ 命中普通规则 → 节点定义转 chain
         └─ 全不命中 → fallback；无 fallback 用旧链兜底
                    │
                    ▼
        resolveChain（角色/指定人）→ applyAssignees → createApproval（快照）
                    │
                    ▼
        decide（原有逐级 + 管理员代审/一键通过）→ applyBusiness（原有联动）
```

新模块 `src/approval-flow.js` 导出 `resolveApprovalChain(bizType, context)`：

```js
{
  engine: 'legacy' | 'custom',
  chain: [{ role, label, mode, user_id, stage, allow_change, on_missing, ... }],
  meta: { flowId, version, ruleId, ruleName, source, autoApprove }
}
```

`chainForDiscount` / `chainForContract` 保留不删，作为 legacy 分支与兜底。预览接口和提交接口共用同一函数，避免「预览说要经理、提交却走总监」。

**合同初始状态**：由节点 `stage` 推导，`sales`/缺省 → `sales_review`，`finance` → `finance_review`，`legal` → `legal_review`；缺省时仍按旧角色表兜底。

## 7. 审批人解析增强

| 模式 | 解析方式 | 候选人列表 |
|---|---|---|
| `role` | 调 `approverCandidates(orgId, role)`，取最近的一个 | 组织树全部候选，供改选 |
| `user` | 校验用户存在且在职，直接使用 | 单人 |

补充规则：

1. **缺人**：默认 `block`（阻止提交并提示节点名）；`admin` 时转系统管理员并留痕。
2. **重复**：`skip_duplicate=1` 时跳过与上一节点相同的人；全被跳过则走免审批。
3. **自审**：`allow_self=0` 时顺延到下一候选人；无候选人按 `on_missing` 处理。
4. **改选**：`applyAssignees()` 同时接受 `{ 角色: userId }`（旧）与 `{ 节点序号: userId }`（新）。
5. **离职/停用**：解析时过滤 `status='active'`；已发起单据保留原 `approver_id`。

## 8. 接口设计

挂在 `/api/settings/approval-flows` 下；读接口所有登录角色可用，写接口仅 `admin`。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/settings/approval-flows` | 两类单据的规则、节点、当前引擎、官方预设版本、阈值、角色与用户 |
| POST | `/api/settings/approval-flows/clone-active` | 把当前启用版本整批克隆为下一版草稿（可视化编辑入口） |
| PATCH | `/api/settings/approval-flows/:id` | 修改单条草稿规则的条件与节点 |
| POST | `/api/settings/approval-flows/publish` | 整批发布该类型的草稿版本，旧版全部转 `disabled` |
| DELETE | `/api/settings/approval-flows/:id` | 仅草稿可删；官方预设与兜底规则禁止删除 |
| POST | `/api/settings/approval-flows/restore-official` | 停用自定义版本并重新激活官方预设 |
| POST | `/api/settings/approval-flows/preview` | 样例字段试运行，返回命中规则、审批人、告警 |

读取对全部登录角色开放；除试运行外，写接口统一要求 `admin`。

校验示例：`节点 2 未选择审批人`、`条件引用未知字段 discount`、`指定用户已停用`、`同一单据已有启用中的流程`。

变更写 `audit_logs`：`target_type='approval_flow'`，`detail` 记录规则名、版本与来源变化。

## 9. 可视化设计器交互

### 9.1 页面结构

```
系统设置
┌ 审批流程设计器 ────────────────────────────────────────────────┐
│ 当前：[官方预设 v1 · 已启用]   [可视化编辑] [恢复官方预设] [试运行] │
│ 切换：报价折扣 | 合同审批                                        │
├──────────────────────────────┬─────────────────────────────────┤
│ 画布（规则泳道）              │ 属性面板                         │
│ ① 优先级10 零折扣免审         │ 选中节点：                       │
│    [折扣率=0] → [免审批]       │   名称：销售总监                 │
│ ② 优先级20 经理审批           │   审批人来源：角色 / 指定人       │
│    [0<折扣≤经理限额]           │   角色：销售总监                 │
│      → [部门经理] → [结束]     │   允许改选 / 缺人转管理员         │
│ ③ 优先级30 经理+总监          │   跳过重复 / 意见必填             │
│    [折扣>经理限额]             │                                 │
│      → [经理] → [总监] → [结束] │ 试运行：                        │
│ ⋮ 拖拽手柄调整优先级           │   折扣 12% → 命中③               │
│ [+ 新建规则] [+ 条件] [+ 节点] │   张三 → 李四 → 王五            │
└──────────────────────────────┴─────────────────────────────────┘
```

### 9.2 画布元素

| 元素 | 形态 | 操作 |
|---|---|---|
| 规则泳道 | 横向卡片，顶部显示优先级 / 名称 / 来源徽标 / 拖拽手柄 | 拖动改优先级；点击选中 |
| 条件芯片 | 圆角标签，如「折扣率 > 10%」 | 点击在属性面板编辑；`+` 新增；`×` 删除 |
| 节点芯片 | 带序号的卡片，如「1 部门经理」 | 点击编辑；拖动改顺序；节点间用箭头连接 |
| 结束节点 | 「通过」或「免审批（直接通过）」 | 免审批规则只允许 0 个审批节点 |
| 属性面板 | 右侧抽屉 | 随选中元素切换内容 |
| 试运行 | 底部样例输入 + 高亮命中泳道 | 只读取配置，不改数据，非管理员也可用 |
| 审批人池 | 节点编辑区下方的角色 / 人员芯片 | 拖到节点上即设为该节点审批人；`'role'` 或 `'user'` 模式自动切换 |
| 角色权限池 | 用户与组织页表格上方的角色芯片 | 拖到成员行「角色」列授权；把成员角色芯片拖回池中回收；沿用原分级管理校验 |

### 9.3 关键交互规则

1. **官方预设只读**：`source='official'` 的规则不能直接改字段；点「可视化编辑」先 `clone`，新草稿 `source='custom'`，改完发布才生效。
2. **发布前对比**：展示与当前生效版本的差异（新增 / 删除 / 修改的节点与条件），确认后发布。
3. **草稿可丢弃**：未发布的草稿不参与求值；发布失败不破坏当前生效版本。
4. **恢复官方预设**：一键停用自定义版本并重新激活 `official`，保留审计记录。
5. **权限**：`admin` 可编辑、发布、恢复、试运行；其他角色只读且可试运行。
6. **技术选型**：原生 HTML5 drag 事件 + CSS 连接线，不引入流程图库；画布状态与 `/api/settings/approval-flows` 的 JSON 一一对应，避免「图画的和实际跑的不一致」。
7. **样式**：复用 `public/css/app.css` 的 `.setgrid / .setcard / .grid / .notice / .chain-preview`，新增 `.flow-canvas / .flow-lane / .flow-node / .flow-conn / .flow-chip`。

## 10. 兼容、迁移与回滚

1. **新装**：安装向导写官方预设 + 开关 `'1'`，开箱即用的流程与现在内置链一致。
2. **升级**：DDL 只建表补列；开关读默认 `'0'`，不插规则，行为不变。
3. **老阈值**：官方预设用计算字段引用阈值，改阈值预设同步变化；自定义规则用原始字段时需在页面标注「此规则不随阈值变化」。
4. **进行中审批**：`approval_steps` 是快照，配置改动不回溯；详情展示「按 vN / 官方预设生成」。
5. **回滚**：关开关回到旧链，或点「恢复官方预设」；已发出的单据仍按原规则走完。
6. **双引擎**：SQL 同时兼容 SQLite / PostgreSQL；不用 `julianday`、`insert or replace` 等方言；JSON 解析在 JS 层。

## 13. 待确认设计决策

| 决策点 | 建议方案 | 影响 |
|---|---|---|
| 新装默认 | 官方预设启用，与内置链等价 | 开箱即用，老实例升级不受影响 |
| 官方预设能否直接改 | 不能，先克隆为草稿 | 保留一键恢复，避免改坏默认流程 |
| 老阈值与预设关系 | 预设用计算字段引用阈值，同步变化 | 不用维护两套金额；自定义规则可脱离阈值 |
| 0% 免审 | 做成预设里的 `auto_approve` 规则 | 管理员可在设计器里改成必须审批 |
| 缺人默认策略 | `block`，可选转管理员 | 不静默跳过 |
| 进行中单据 | 不回溯 | 安全；改流程需等单据走完或管理员代审 |
| 会签 / 并行 | 首期不做 | 需改状态机，单独排期 |
| 配置权限 | 仅 `admin`（超级管理员）可改，其他角色只读 + 试运行 | 与系统设置一致 |
